# Auxiliary spatial evidence

This directory contains secondary evidence used to guide manual verification of
the three Experiment 1 sites. It is deliberately separate from
`world_model/vector/` and must not be merged into the frozen observed layers
without an author-recorded verification step.

## Evidence classes

- `visual_candidate`: a feature interpreted from a public imagery tile. It is
  useful for identifying what a surveyor should check, but it is not a survey
  observation and has no admissible height, width, slope, or legal status.
- `ml_footprint_candidate`: an automatically detected or conflated building
  footprint from a machine-learning/open-data source. It is a secondary
  two-dimensional candidate and does not provide measured height.
- `context_only`: elevation or imagery metadata used for orientation only.
- `lidar_derived`: a height or footprint calculated from an identified public
  LiDAR product. It is admissible for remote-sensing analytical comparison,
  with low/high sensitivity, but is not a field or engineering measurement.

The Experiment 1 evaluator must continue to use the required design-package
layers and the frozen world model. Image-only candidates cannot be promoted to
observations. The frozen London and Chicago LiDAR derivatives may calculate an
analytical Existing shade baseline through explicit `central`, `low`, and
`high` runs; they cannot establish accessibility or regulatory compliance.

## London and Chicago public height layers

`london_public_height_proxy.gpkg` combines the Environment Agency 1 m DSM and
DTM with the 2022 Vegetation Object Model. Within the registered Mitre Yard
polygon, all three intersecting OSM building footprints have LiDAR-derived
height and two vegetation crown components pass the size filter. The 36 OSM
buildings and eight OSM trees reported elsewhere are context-catchment counts,
not formal-site counts.

`chicago_public_height_proxy.gpkg` combines the City of Chicago Building
Footprints dataset with the 2019 USGS 3DEP 2 m height-above-ground raster.
Within the study-defined 40 m corridor, 12 official footprints intersect the
boundary, ten have an evaluable LiDAR or stories-based height, and three
non-building components pass the crown size filter. Continuous elevated
infrastructure is rejected as a crown candidate. The corridor remains an
analytical envelope, not a parcel or legal right-of-way.

Both products are rebuilt by
`build_london_chicago_public_height_layers.py`; completeness and claim limits
are recorded in `london_chicago_public_height_completeness.json`.

## Accessibility proxy layers

`london_accessibility_proxy.gpkg` contains three OSM service-route candidates
inside the formal London boundary. Width is a perpendicular geometric clear
corridor between mapped buildings/barriers and the boundary. `chicago_accessibility_proxy.gpkg`
contains 14 OSM footway candidates matched to the City of Chicago sidewalk
polygon file (dataset `77cn-6x4c`, clipped to the analysis envelope). Both use
public LiDAR DTM multi-scale plane fits for longitudinal and cross-terrain
gradients. The route and turning layers are explicitly `remote_sensing_proxy`
or `official_sidewalk_geometry_proxy`, not measurements.

The packages are rebuilt by `build_london_chicago_accessibility_proxy.py` and
summarized in `london_chicago_accessibility_completeness.json`. The 2 m
Chicago DTM cannot resolve a 1--2 m sidewalk's actual cross-slope, so that
field must not be used as an ADA compliance claim without a survey.

## Suzhou visual audit

`suzhou_visual_audit.json` records the Esri World Imagery tile request covering
the registered Xutai Road grass parcel. The image confirms visible vegetation
inside the analytical polygon and is therefore evidence that the empty OSM tree
layer needs manual checking; it does not provide tree height or crown radius.

The imagery file is kept as a local audit artifact rather than redistributed in
the study package. Its URL, retrieval time, tile range, and SHA-256 are recorded
in the audit record.

`suzhou_image_proxy.gpkg` is the reproducible numerical proxy package created
by `build_suzhou_image_proxy.py`. It contains 12 tree candidates, one path
candidate, and one turning-space candidate. The central numerical fields may be
used in the formal analytical proxy run only when the corresponding low/high
fields are run as mandatory sensitivities. Every feature remains marked
`not_measured`, and engineering or compliance use is prohibited.

## Existing proxy evidence outputs

`formal_proxy_designs/suzhou_existing_{central,low,high}.gpkg` are the seven-layer
Existing packages generated by `preregistration/prepare_existing_condition_designs.py`.
For each variant, the adjacent `suzhou_existing_{variant}_evidence/` directory
contains `need_results.csv`, `constraint_results.csv`, and a JSON evidence record
generated by `build_suzhou_proxy_evidence.py`. The evidence record stores the
evaluator predicates and conservative fail rules used when the image proxy has
no furniture, species, maintenance, or resident-elicitation evidence.

The resulting five-outcome JSON files are evaluable computational records only;
`all_five_evaluated=true` means that every registered metric received a value,
not that the proxy is a field-verified baseline. `SUZ-C01`--`SUZ-C09` are
confirmed for inclusion as analytical screening rules. An individual run still
records a rule as `not_evaluable` when its frozen trigger or design-output
evidence is absent. None of these files is legal, engineering, permit, or
resident evidence.

## Acceptance rule

An auxiliary feature may be promoted to an observed input only when a named
operator records the verification method, source file, date, coordinate
reference system, positional uncertainty, and the fields actually measured.
Unverified or missing measurements remain `not_evaluable`.
